What makes this a real application, not toy routing

Engineering credibility · numbered on the diagram

The handoff diagram above is the happy path. In production each numbered point is a concrete engineering control — classification, context, fallbacks, keyless auth, observability and independent versioning.

1

Intent classification at the orchestrator

voice_orchestrator triages every turn and picks a route before any handoff — not keyword matching. The chosen route drives handoff_to_card_agent / handoff_to_mortgage_agent.

2

Conversation context carried across handoff

The specialist inherits the known customer and full turn history, so the handoff is seamless — the customer never repeats themselves.

3

Wrong-specialist detection → re-handoff

If a turn is routed to the wrong agent, it is detected and re-handed to the correct specialist instead of answering incorrectly.

4

Tool timeouts → fallback

A slow or failed tool call (e.g. get_available_meeting_times) retries or returns a safe response rather than dropping the turn.

5

Keyless backend auth on tool calls

Backend tools authenticate with DefaultAzureCredential — no secrets live in prompts or the model context.

6

Tracing / observability hook

Every turn, handoff and tool call emits OpenTelemetry spans to Azure AI Foundry Observability — see the companion foundry-engineering-replay.html trace.

7

Independent versioning

The orchestrator prompt, the specialist prompts and the tool contracts are versioned and deployed separately — a specialist fix ships without redeploying the orchestrator.
